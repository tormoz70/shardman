### Roadmap к v1.0 (Production Readiness)

Поскольку ядро (Control Plane) теперь надежно, фокус следующего ревью должен сместиться на **клиентскую часть, отказоустойчивость и эксплуатацию**. Вот 4 направления, которые нужно проработать перед выкаткой в прод.

#### 1. Клиентский кэш и gRPC Streaming (Убираем 99% трафика)
Сейчас `shardman-server` отвечает на каждый `ResolveWrite`. Это быстро, но сеть и сериализация protobuf все равно создают задержку (latency).
*   **Решение:** Реализуйте метод `WatchTopology` (gRPC Server Streaming) в вашем API.
*   **Как это работает:**
    1. Клиент при старте запрашивает полную таблицу маршрутов и текущий `topology_version`.
    2. Клиент делает **локальный in-memory резолв** (O(1) без сети).
    3. Клиент держит открытый стрим `WatchTopology`.
    4. Как только `SealRotate` или `PromoteStandbyToActive` инкрементят версию, ваш `topology.Broadcast` (который я видел в коде) пушит новую версию в стрим.
    5. Клиент получает уведомление, сбрасывает локальный кэш и делает один `Resolve` запрос для обновления.
*   **Итог:** Нагрузка на `shardman-server` падает почти до нуля, задержка для приложений стремится к нулю.

#### 2. Heartbeats и защита от "Мертвых шардов"
В `UpdateStats` агент шлет `reported_bytes` и обновляет `last_seen_at`. Но что если Postgres упал, а агент продолжает слать метрики (или агент тоже упал)?
*   **Проблема:** Если шард недоступен, `ResolveWrite` все равно вернет его DSN клиенту. Клиент получит таймаут подключения.
*   **Решение:**
    *   Добавьте в `seal.Supervisor` (или отдельный `health.Supervisor`) цикл, который проверяет `last_seen_at`.
    *   Если `time.Since(last_seen_at) > HeartbeatTimeout` (например, 60 сек), шард должен быть переведен в состояние `fsm.StateDead` или исключен из `ShardsForBucketRead`.
    *   Для `ResolveWrite` это критично: если active-шард "умер", control plane должен уметь форсированно инициировать `SealRotate` на standby-шард, чтобы приложение не потеряло возможность писать.

#### 3. Database Contention и Statement Timeouts
Теперь, когда у вас тяжелые транзакции с `FOR UPDATE SKIP LOCKED` и `bumpTopologyVersionTx`, Metadata DB становится центром кристаллизации всех блокировок.
*   **Риск:** Если один из процессов (например, `retention.Supervisor`) "зависнет" или будет удерживать лок слишком долго, пул соединений `pgxpool` иссякнет, и весь control plane встанет.
*   **Решение:**
    *   В DSN для Metadata DB жестко пропишите `statement_timeout=5s` (или `10s`). Никакая операция в control plane не должна держать транзакцию дольше пары секунд.
    *   Убедитесь, что `pool.MaxConns` в `pgxpool.New` адекватен количеству горутин в супеврвайзорах + количеству одновременных gRPC воркеров.

#### 4. Динамическое обновление конфига (На будущее)
Сейчас `ClusterConfig` кэшируется навсегда (так как он меняется только при `Bootstrap`). Это отлично.
Но если в будущем вы захотите добавить gRPC метод `UpdateConfig` (например, чтобы на лету менять `shard_max_bytes` или `retention_depth` без перезапуска кластера), вам понадобится механизм инвалидации:
```go
func (s *Store) UpdateConfig(...) {
    // ... UPDATE в БД ...
    s.configCache.Store(nil) // Инвалидация кэша
    s.Broadcast.Notify(newVersion) // Уведомление клиентов и супервайзеров
}
```

### Что добавить в observability (Метрики)
У вас уже есть OpenTelemetry и Prometheus. Убедитесь, что на дашбордах есть следующие графики, они спасут вам жизнь при дебаге:
1.  **`shardman_topology_version`** (Gauge) — если график встал, значит у вас проблемы с коммитами в Metadata DB.
2.  **`shardman_resolve_cache_hits_total`** vs **`shardman_resolve_db_reads_total`** (если кэш конфига начнет сбоить, вы это сразу увидите).
3.  **`shardman_seal_duration_seconds`** (Histogram) — сколько времени занимает процесс `active -> sealed -> promote_standby`. Если это занимает больше 1-2 секунд, приложения будут получать ошибки записи (так как active шард уже не принимает writes, а новый еще не промотился).
